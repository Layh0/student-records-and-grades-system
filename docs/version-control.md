# Работа с Git

## Состав репозитория

В Git хранятся исходный код C#/XAML, проекты и решение, тесты и документация. Не хранятся `bin/`, `obj/`, настройки IDE, результаты тестов, временные файлы, локальные настройки и секреты. `.gitignore` не удаляет уже отслеженные файлы: для них используется `git rm --cached`. Проверка: `git ls-files | grep -E '(^|/)(bin|obj)/'`, `git check-ignore -v путь` (для неотслеживаемых файлов).

Нельзя публиковать пароли, токены, закрытые ключи или строки подключения с секретами. Если секрет попал в Git, сначала отозвать и заменить его, затем оценить очистку истории и всех копий; один `.gitignore` задним числом не помогает.

## Ветви и слияние

`main` содержит объединённый результат. Для каждого этапа создаётся своя ветка `stage/NN-название` от актуального `main`. На этапе 3 допустимы дополнительные `feature/*` для моделирования команды, их объединяют в ветку этапа. Перед объединением проверить статус, различия, сборку и тесты, а после - результат слияния. Никаких force-push в общую историю.

## Коммиты

Каждый коммит содержит одну логически связанную задачу и сообщение в форме `тип: действие`, например `docs: document module contracts` или `fix: validate grade range`. Перед коммитом проверить `git diff` и `git status`; коммиты отправлять в соответствующую удалённую ветку. Учебная контрольная точка отмечается тегом `stage-02-checkpoint`.

## Учебный конфликт

Разрешение конфликта фиксируется в отчёте этапа 2. Для воспроизведения использованы две независимые правки одной строки: одна временно сохранена в `git stash`, другая закоммичена в той же ветке. При `git stash apply` Git показал конфликт; маркеры были удалены после выбора согласованного содержания, затем файл добавлен в индекс и закоммичен. Это упражнение не имитирует слияние двух реально существующих участников команды.

Полезные команды: `git status`, `git diff`, `git log --oneline --graph --decorate --all`, `git branch -a`, `git tag`.
