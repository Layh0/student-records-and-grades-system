# Этап 2. Система контроля версий

## Исходное состояние

Начало: чистая ветка `main` после слияния этапа 1, коммит `b1068fb`. Создана ветка `stage/02-version-control`. В существующем `.gitignore` была только `.vs/`, а семь файлов `obj/` уже отслеживались.

## Изменения

Расширены правила игнорирования сборки, IDE, временных файлов и секретов, из индекса удалены семь производных файлов `obj/` (история прежних коммитов не переписывалась). Добавлены `.editorconfig` и [правила Git](../version-control.md). Создан тег `stage-02-checkpoint` на коммите разрешения конфликта. Этап включает более пяти осмысленных коммитов, отправленных в одноимённую удалённую ветку.

## Учебный конфликт

На базе `85b6f13` в файле `docs/conflict-exercise.md` одна правка строки была сохранена через `git stash`, вторая - закоммичена (`5333758`). `git stash apply` завершился кодом 1 и сообщил `CONFLICT (content): Merge conflict in docs/conflict-exercise.md`. Маркеры конфликта были заменены общим вариантом: сначала форматирование, затем сборка и тесты; результат закоммичен как `2b22a1c`. Сохранённая запись stash удалена. Это учебный конфликт с применением stash, а не слияние двух веток.

## Проверка

- `git check-ignore -v` подтвердил правила для примеров `obj`, `bin`, `.vs` и `.env`.
- `git ls-files | grep -E '(^|/)(bin|obj)/'` не вывел отслеживаемых файлов.
- `git log --oneline --graph --decorate --all` показал ветку этапа, последовательные коммиты и тег.
- Код приложения не изменялся, поэтому сборка и тесты на данном этапе не запускались.

Основной риск: `.gitignore` не защищает от принудительного добавления или уже опубликованного секрета; требуется проверять изменения и при утечке отзывать секрет. Вывод: репозиторий подготовлен для последующих этапов, история изменений и контрольная точка доступны для проверки.
